# 05 · 作业队列

> **一句话**：世界生成是长任务，必须排队、可观测、可取消、崩溃能恢复——但同一时刻只跑一个。

你是**调度室的值班员**。这一轮搭"作业"这一层：谁在跑、排了几个、跑到哪、失败了怎么办。

### 步骤 1 · 作业记录

在 `runtime/jobs/{job_id}.json` 存每个作业。字段固定：

`job_id`（可读格式：`YYYYMMDD-HHMMSS-四位随机`）、`kind`（`worldgen` / `ringgen` / `test`）、`status`（`queued` / `running` / `succeeded` / `failed` / `canceled`）、`created_at`、`started_at`、`ended_at`、`exit_code`、`cmd`（字符串，仅供展示）、`args`（数组）、`stages_done`（数组）、`progress`（0~100）、`artifacts`（数组，产物路径）、`error_tail`（失败时最后 20 行）。

### 步骤 2 · 队列语义

- **单并发**：任何时刻最多一个 `running`。其余 `queued`，按入队顺序 FIFO。
- **去重**：同 `kind` 且参数完全相同，若已有 `queued` 或 `running`，不重复入队，直接返回已有 `job_id`，并以自动消退的轻提示说明"已有一个相同作业在跑"；不弹出作业管理面板。
- **取消**：允许取消 `queued`（直接标 `canceled`）与 `running`（发中断，10 秒不退出则强杀，标 `canceled`）。
- **失败重试**：只允许手动重试，自动重试不做（世界生成失败经常是真问题，静默重试掩盖问题）。

### 步骤 3 · 持久化与恢复

进程重启时读 `runtime/jobs/*.json`：把 `running` 但无对应 PID 的作业标 `failed`，`error_tail` 写"进程丢失"；`queued` 保持排队并继续执行（或按配置改为 `canceled`，默认继续）。

每一步状态变化都追加一条对应事件到 `runtime/events.jsonl`（`job.enqueued` / `job.started` / `job.succeeded` / `job.failed`）。

### 步骤 4 · 普通游戏反馈与开发作业详情

后台队列不因界面关闭而停止，也不把游戏变成作业管理页。两种呈现严格分开：

- **普通游戏**：只在存在与当前世界相关的活动作业时，于现有目标/状态区域附近显示一条轻量进度，包含简短阶段、百分比和必要的取消操作；不展示完整队列、命令、路径或日志。没有活动时完全不占位。
- 排队、去重、完成与失败使用零件 08 的自动消退通知。失败后普通游戏只在相关创建/暂停界面提供重试，不展开 `error_tail`。
- **开发工具**：显式打开后才显示完整作业详情。当前作业含阶段名、已用时间与取消按钮；队列最多列 3 条，其余显示 "+N 更多"；已结束作业列最近 3 条，成功绿点/失败红点，点击可展开 `error_tail`。
- 开发作业详情是可关闭界面，不在左栏、右栏或日志区常驻；空态不渲染卡片，也不为了展示"没有作业"而占用 HUD。

### 步骤 5 · 与开发终端打通

开发 CLI 输入 `jobs` 时列出全部作业（等宽表格：id / kind / status / 用时），输入 `jobs cancel <id>` 取消。命令与表格只在零件 04 的开发终端可见，普通游戏不需要执行任何命令。

### 步骤 6 · 测试作业

在开发工具内置一个 `test` 作业：spawn 一条会循环打印 5 次并 sleep 的命令（用 `node` 或 `python` 的短内联语义，不要落一个测试脚本文件在项目根），跑到 40% 时"假装"报错，用来验证失败路径。测试按钮不放普通 HUD。

连点 3 次「测试作业」：只能有 1 个 running，2 个 queued（去重若同参数，则应只入 1 个并提示）。

自检截图存 `renders/app_step05_*.png`，至少包含后台运行时的默认轻 HUD，以及显式打开的开发作业详情；不得用固定侧栏或常驻日志充当验收画面。

## 参数表

| 参数 | 默认 | 说明 |
|---|---|---|
| `MAX_CONCURRENT` | 1 | 不要调大，Blender 抢 GPU 会双输 |
| `JOB_TIMEOUT_S` | 900 | 世界生成上限 |
| `KILL_GRACE_S` | 10 | 中断后强杀宽限 |
| `HISTORY_KEEP` | 50 | 保留作业文件数，超出删最旧（succeeded 优先删） |
| `RESUME_QUEUED` | 是 | 重启后是否继续排队作业 |

## 验收标准

1. 连点 3 次测试作业 → 1 running / 其余 queued 或去重提示。
2. 取消 running 作业，进程真死，状态为 `canceled`，事件流有记录。
3. 杀掉 dev server 再起，`running` 变 `failed`，队列状态正确恢复。
4. 失败作业能在显式打开的开发工具中展开看到 `error_tail` 最后 20 行；普通游戏没有完整日志与作业详情。
5. `jobs` 命令只在开发终端输出表格，格式正确。
6. 后台运行时默认游戏仅有轻量进度与自动消退通知；关闭开发详情后回到原玩家与相机，无输入穿透。
7. 默认轻 HUD 与开发详情两类截图均已保存，不以三栏、固定侧栏或常驻作业卡通过验收。

## 回退方案

- **找不到 PID 对应进程**：Windows 用 `tasklist /FI "PID eq <pid>"` 判定；判定不可靠时一律视为已死，标 `failed` 并在 `error_tail` 注明。
- **文件锁冲突**（前端与服务端同时写）：所有作业文件只由服务端写，前端只读。
