# 10 · 灵感引擎 · 世界设定卡

> **一句话**：用户一句"我想要会下雨的火山岛"，变成一份**卡**；Blender 只认这张卡，AI 不碰代码。

---

## 前置

零件 09（模型可调）。无 Key 时走离线模式，本零件仍必须能产出合法卡。

---

## 提示词正文

你是**翻译官**。你的产物不是代码、不是场景，而是 `specs/world_spec.json`。

### 步骤 0 · 先看 provider 能力（不要硬要求模型做不到的事）

零件 09 的探测结果决定你怎么发请求，**一个提示词不能假设所有模型都支持 JSON 模式**：

| 探测结果 | 你的做法 |
|---|---|
| 支持严格 JSON 模式 | 直接开 JSON 模式，`system` 里仍写"只输出 JSON"作双保险 |
| 不支持 JSON 模式 | 关掉 JSON 模式；在 system 里强调"你的回复必须以 `{` 开头、以 `}` 结尾"，并把温度降到 0.7 |
| 上下文小（< 4k） | 丢掉"灵感例句"，只留硬约束 + 字段清单；字段说明压缩到一行 |
| 只有文本能力 | 一样能跑；解析走步骤 4 的宽松路径 |

在汇报里写明这次实际用到哪一档。

### 步骤 1 · 两种输入

**A. 自由描述**：用户输入一段话或一句话。
**B. 卡牌 + 滑杆**（零件 11 产出）：三张卡（地形 / 材质 / 天气或情绪）+ 六根滑杆（起伏、水量、植被、奇诡、暖冷、拥挤）。

两种输入都要归一到同一个请求：把它们拼成一段"愿望"，再加上**邻域约束**（扩环时用，见步骤 6）。

### 步骤 2 · 给 AI 的提示词（核心）

你写给模型的系统提示词，要点如下（用中文写清、用第二人称）：

- 你是世界设定师，只输出一份 JSON，不要解释、不要 markdown 代码围栏。
- 世界是**低多边形、可爱、童话感**，不要写实，不要阴暗恐怖（除非用户要求）。
- 必须包含契约 F 的全部字段，字段名不得改动，不得增删顶层字段。
- 必须给出 `regions`（1~5 个）——**这是"世界有分区"的来源**，不是可选装饰。每个区给 `elevation`/`moisture`/`temperature`/`tree_mix`/`note`，`note` 要写成人话（"背风坡，土更干"）。
- 必须给出 `time`（起始时刻 + 一天多长）与 `weather`（起始天气 + 多频繁才换）。用户说"会下雨的火山岛"，就该让 `weather.kind=rain` 且 `frequency` 偏低（雨常驻），而不是随机给个 `clear`。
- 必须给出 `creatures`（五类动物的有无与多寡）。沙漠不该有大量萤火虫，雪原不该有蝴蝶——**让生物分布像这个世界**。
- `palette` 十个颜色要**互相和谐**：给一个主色相，其余围绕它做明度/饱和度变化；天空和水的颜色要能同时出现不打架。
- `mood` 一句中文，不超过 24 字，要具体（"雨后的苔藓味" 好于 "宁静"）。
- `landmarks` 0~3 个，每个给 `kind`（只能从六种里选）与一句 `note`。
- `regions` 的 `note` 与 `mood` 不要重复用词；区域描述要具体到能指导地形（"北侧迎风，岩多" 好于 "山地"）。landmark 要和 biome 说得通（沙漠里放灯塔要有理由，可以在 note 里写）。
- `weirdness` 越高，允许出现不合常理但可爱的元素（漂浮的石块、蓝色的草、倒着长的树）。
- 输出前自检：颜色是合法十六进制、数值在范围内、枚举值合法。

### 步骤 3 · 用户提示词

把用户愿望原文贴进去，并追加：

- 当前已有哪些环（若扩环）
- 上一环的关键字段（`biome`、`palette` 主色相、`terrain` 数值、`mood`）
- 明确要求：**保持同族**，只做渐变，不做突变（例外：用户明确要求"完全不同的地方"）
- 如果是第 0 环：要求"能一眼看懂、有中心地标、适合作为出生点"

### 步骤 4 · 解析与校验（宽松解析 + 严格钳制）

按这个顺序处理模型返回：

1. 去掉可能的代码围栏、前后废话，取第一个平衡的 JSON 对象。
2. 缺顶层字段：用契约默认值补。
3. 类型不符：尝试转换（字符串数字 → 数字）；转不了用默认。
4. 枚举非法：映射到最近的合法值（例如 `forest` → `island`），并记录一次 warning。
5. 数值钳制：所有范围按契约 F 收进区间。
6. 颜色非法：用当前 `palette` 的同类槽位补齐，或从主色推导。
7. `trees.weights` 归一化（和为 1）。
8. `landmarks` 超过 3 个就截断；`kind` 非法就丢弃该项。
9. 结果写入 `specs/ring_{n}.json`（第 0 环同时写 `specs/world_spec.json`），并写一份 `specs/ring_{n}.md` 可读摘要（给用户看的一页纸）。

**校验不通过不抛错**：钳制后照常出卡，但在摘要里列"修正了哪些字段"。这是本零件的灵魂：**永远有卡**。

### 步骤 5 · 种子

seed 不由模型决定。规则：第 0 环取当前时间毫秒的稳定哈希（用户可手填）；第 n 环 seed = 父环 seed 与 n 的确定性混合（具体算法见零件 12，这里只调用）。模型若在 JSON 里给了 seed，**忽略**。

### 步骤 6 · 邻域约束（扩环用）

扩环请求必须带上：

- 父环的 spec 全文
- 新环的方位（北/东/南/西/东北…，由触发器所在边决定）
- 一句硬约束："`biome` 必须与父环相同或相邻（如 island ↔ swamp / volcanic ↔ desert 视为相邻）；`palette` 的色相偏移不超过 ±30°；`terrain.roughness` 变化不超过 0.2；`mood` 必须读起来像同一个世界换了天气。"

### 步骤 7 · 提示词要"给灵感"

除硬约束外，在提示词里塞一小段"灵感例句"（每条不超过 12 字，随机抽 5 条给模型看，例如：会发光的蘑菇林 / 退潮后露出的鲸骨 / 云在脚下流 / 一座只在下雨时出现的桥 / 草会跟着史莱姆转头）。**不要**让模型照抄，只当气味。

### 步骤 8 · 自检（四种输入都要过）

1. 「一个会下雨的火山岛」
2. 「雪原，但有一棵巨大的树」
3. 三张卡：苔藓 + 鲸骨 + 黄昏，滑杆全中位
4. 扩环：从 island 向北扩

每种都要：`specs/` 下出现合法 JSON、摘要 md、钳制记录；把生成的 `biome`、`mood`、主色截图或文本贴进汇报。

## 验收标准

1. 四种输入都能产出 `specs/ring_{n}.json`，字段齐全、类型正确、数值在范围。
2. 每次都有 `specs/ring_{n}.md` 摘要，且列出修正记录（若无可写"无修正"）。
3. 扩环结果与父环"同族"：`biome` 合法相邻、色相偏移 ≤30°（用色相差算，写进汇报）。
4. 同一用户输入连续两次，seed 不同、结果不同（证明不是硬编码）。
5. 模型返回垃圾（人为喂一段乱码当响应）时，仍出卡并标注"已兜底"。
6. 没有把 Key 打进任何 spec 或日志。

---

## 回退方案

- **模型只会返回带围栏的 markdown**：解析器要能剥三种围栏：带 json 标记的、无标记的、以及只有开头没有结尾的。
- **返回被截断**：优先尝试"补全尾部"（补 `}` 与 `"`）；失败则走零件 13 的"半成品修补"。
- **模型完全不听话**（返回散文）：直接走零件 13。
