# 30 · 拓荒解锁状态机

> **一句话**：一次蓄力满，Blender 写一张请求单，网页服务端接单跑后台生成，跑完写结果单；Blender 读到结果才开雾。

---

## 前置

零件 06（能跑后台作业）、零件 28、29。

---

## 提示词正文

你是**仪式主持人**。整个"拓荒"的生命周期由你管：谁现在在做什么、失败了怎么办、结果怎么落盘。

### 步骤 0 · 跨进程桥（先定这个，否则一定卡住）

蓄力发生在 **Blender 里**（零件 29 按 E），但作业队列、AI 调用、网页通知都在 **网页服务端**。两边必须有一条明确的桥，**不要**靠 MCP 让网页去反向操控 Blender。

**桥 = 一个请求文件 + 一个结果文件**：

| 文件 | 谁写 | 谁读 | 内容 |
|---|---|---|---|
| `runtime/unlock_request.json` | Blender（蓄力满时原子写入） | 网页服务端（每 500ms 轮询） | `request_id`、`ring_from`、`direction`、`player_pos`、`created_at` |
| `runtime/unlock_result.json` | 网页服务端（状态机结束或失败时） | Blender（轮询或下一帧读） | `request_id`、`status`（`ok`/`failed`）、`ring_new`、`error`、`finished_at` |
| `runtime/world_state.json` | **只有网页服务端状态机写** | 两边都读 | 唯一真相 |

规则：

1. Blender 只**申请**（写 request），不直接入队、不调 AI。
2. 网页服务端是**唯一**执行者：读 request → 走 AI → 入队作业 → 应用产物 → 写 state → 写 result。
3. Blender 每 0.5 秒读一次 `unlock_result.json` 的 `request_id`：
   - 匹配且 `ok` → 播放开雾动画（REVEALING 在 **Blender 侧**播，因为雾是 Blender 里的东西）。
   - 匹配且 `failed` → 恢复雾、给失败提示。
   - 超时 300 秒无结果 → 视为失败。
4. `request_id` 用"时间戳 + 4 位随机"生成，用来防止读到上一轮的旧结果。
5. 两边都**先读后写、原子替换**；网页服务端对 request 做去重（同一个 `request_id` 只处理一次）。

**这一点写错，整个拓荒就是两套互不相干的逻辑各自跑。** 如果你在实际施工时发现更顺的做法（例如用 MCP 事件推送），可以换，但必须在汇报里说明，并保持"只有一个执行者"这条底线。

### 步骤 1 · 状态定义

| 状态 | 含义 | 进入条件 | 退出 |
|---|---|---|---|
| `IDLE` | 无拓荒（也是结束态） | 初始 / REVEALING 结束 | 收到 `BeginUnlock` |
| `NEAR_EDGE` | 已在可拓荒区（属于 UI 层，不入此状态机） | — | — |
| `CHARGING` | 蓄力中（零件 29 驱动） | 按下 E | 满或松 |
| `REQUESTING` | 正在写作业 | 满蓄力 | 作业入队成功 |
| `GENERATING` | 后台 CLI 在跑 | 作业 started | succeeded / failed |
| `APPLYING` | 把产物并入场景 | succeeded | 并入完成 |
| `REVEALING` | 雾退动画 | APPLYING 完成 | 1.5 秒后 |

- `REQUESTING` / `GENERATING` / `APPLYING` / `REVEALING` 期间：拒绝新的 `BeginUnlock`，并提示"拓荒进行中"。
- 失败：从 `GENERATING` 回 `IDLE`，雾墙**恢复原状**，给一次可读的失败提示（不弹大窗），允许重试。

### 步骤 2 · 请求（REQUESTING）

按这个顺序做，任一步失败就回滚并回 IDLE：

1. 读 `runtime/world_state.json`（先读再改）。**本状态机由网页服务端执行**，Blender 只写 request、只播开雾。
2. 校验：`ring < MAX_RINGS`（`MAX_RINGS` 是**允许的最高环号**，默认 4，对应 180×180）；该方向未解锁；当前无 running 作业。
3. 调零件 10 生成下一环的设定卡（输入含父环 spec + 方位）。**这一步可以慢**（要等 AI），所以整段在后台跑，页面显示"正在构思新土地…"。
4. 把卡写到 `specs/ring_{n+1}.json`，把 `seed` 写进状态文件（先写"计划中"标记，不增加 ring）。
5. 入队作业：`kind=ringgen`，`script=world/scripts/gen_ring.py`，环境变量带 `MIST_RING=n+1`、`MIST_SPEC`、`MIST_STATE`、`MIST_OUT=world/ring_{n+1}.blend`。
6. 成功入队 → `GENERATING`。

**注意**：AI 生成卡失败不算硬失败，走零件 13 兜底；只有"入队失败"才算失败。

### 步骤 3 · 生成中（GENERATING）

- 转发进度到网页（`job.progress`）：阶段名改写成人类语言（"在种树…"）。
- 网页与 Blender 内都要有"可感知的进行中"：Blender 里雾墙轻微脉动（0.5Hz，振幅 0.5 BU），不要静止。
- 超时（默认 240 秒）：标失败，回滚。

### 步骤 4 · 应用（APPLYING）

**执行者**：网页服务端（它持有状态文件与作业队列；产物由 Blender 后台进程写出）。

作业成功后：

1. 打开产物 `.blend` 或读产物目录（两者取一，见零件 32 的产物约定）。
2. 把新环的对象并入当前场景（不重载整个场景）。
3. 更新 `runtime/world_state.json`：`ring += 1`、`island_size += 20`、`seeds` 追加、`unlocked_chunks` 追加、`landmarks` 追加、`last_generated_at`。
4. 追加事件 `ring.unlocked`。
5. 写 `runtime/chunk_hashes.json` 的新增条目（旧的不动）。

**先备份**：应用前把当前 `world_state.json` 复制一份到 `runtime/backup/world_state_{timestamp}.json`。

### 步骤 5 · 开雾（REVEALING）

**执行者**：Blender 侧（因为雾是 Blender 里的对象）。网页服务端在 APPLYING 完成后写 `unlock_result.json`（`status=ok`、`ring_new`），Blender 读到匹配的 `request_id` 才开始播这段动画。

1.5 秒动画，分三段：

- 0~0.5s：雾墙透明度从 0.65 降到 0.15，并向外扩 20 BU（这一段要让玩家"看见"新土地从雾里浮出来）。
- 0.5~1.0s：新地形从边缘向内"显影"（用材质透明度或裁剪平面扫过）。
- 1.0~1.5s：新边界重新凝雾，透明度回到 0.65。

播放完：`IDLE`，弹通知（零件 08 已接好 `ring.unlocked`）。

### 步骤 6 · 唯一真相与并发

- `world_state.json` 是唯一真相。Blender 与网页都读它，**只有状态机能写**。
- 写：临时文件 + 原子替换；写前读、写后校验（能解析、ring 合法）。
- 并发：以"文件锁 + 进程内互斥"防双写；拿不到锁就等 200ms 重试，最多 5 次。

### 步骤 7 · 可恢复

- 进程在 `GENERATING` 时崩了：重启后读状态文件里的 `pending_ring`，若产物已存在 → 直接进 `APPLYING`；若不存在 → 提示"上次拓荒未完成"，允许重试。
- 状态机当前状态也写进 `world_state.json` 的 `fsm` 字段（`idle`/`generating`/…），供网页显示。

### 步骤 8 · 验收

1. 手动模拟一次完整流程（可用一个"假产物"）：IDLE → … → IDLE，ring +1。
2. 三种失败（AI 卡失败但有兜底、作业失败、超时）都能回 IDLE 并恢复雾。
3. 并发：连点两次蓄力，只有一次生效。
4. 进程崩溃恢复：kill 掉后重启，状态正确。
5. `ring.unlocked` 事件被追加，网页弹通知。
6. 全流程截图/录屏 + 状态文件前后对比。

## 验收标准

1. 七态流转正确，非法转移被拒。
2. 失败必回 IDLE 且雾恢复。
3. `world_state.json` 每次变更都原子、可解析。
4. 并发安全（连点不双生成）。
5. 崩溃后可恢复/可重试。
6. `ring.unlocked` → 网页通知链路通。
7. 状态机 `fsm` 字段被网页正确显示。

---

## 回退方案

- **AI 卡生成太慢**（>90s）：先入队作业，用"占位 spec"（父环 + 轻微扰动），在生成过程中再替换为真卡。汇报说明。
- **产物合并冲突**（对象重名）：新环对象统一加前缀 `R{n}_`，或放进新集合 `W_RING_{n}`，避免与旧环打架。
- **雾退动画掉帧**：把 REVEALING 降级为 0.6 秒的交叉淡入，仍保留"旧雾退去"的观感。
